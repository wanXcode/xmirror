# XPut SEO 改进方案：选好内容，让标题说清楚

方案版本：v1.3，2026-09-28。开发版本：v1.9.8（小版本）。状态：已实现并完成本地验证，待 PR/CI 与发布。标题和摘要全自动生成，可调用现有 AI 接口，无需人工编辑。实现及配置细节见 [v1.9.8 交付说明](xput-seo-v1.9.8.md)。尚未上线。

## 这次要达到什么效果

让真正有用的存档更有机会从 Google 获得访问：先修正后台判断错误，再改善标题和内容筛选，最后用真实搜索数据判断有没有效果。

已有的抓取基础继续使用。首页保持简洁，“值得再读”、页脚导航和统一管理后台延续已确认设计。

依据：[2026-09-28 复审报告](../audits/seo-reaudit-2026-09-28.md)。报告里的 1194 条存档、210 条推荐候选是当时快照，开发和发布前重新核对。

## 第一项：管理员已经放行，系统就要认得

**现在的问题：**内容审核认为可以发布，SEO 模块却可能仍认为没有审核通过。

**怎么改：**内容保存和 SEO 筛选共用有效的审核结论。管理员允许、拒绝或重新审核后，系统重新计算相关页面是否可以推荐给 Google。

“可以发布”和“值得推荐给 Google”仍分别判断。一篇内容可以正常访问，但因为太短、重复或信息不完整，暂不推荐给 Google。

审核共用的是带内容版本的有效结论，不是简单重复调用一次审核接口。原始规则判为可疑、但同版本内容已获有效人工放行时，使用人工结论；管理员封禁、删除或有效人工拒绝仍优先。SEO 定时重评应只读取并计算，不反复创建待审记录或刷审核日志。

拒绝、撤销放行和内容变化先使旧推荐资格失效，再异步重评。后台操作显示“已生效”之前，页面搜索标记、清单及相关缓存必须反映变化；失败要显示“待同步”并持久重试。普通重算暂时失败、但原有内容和审核版本都未变时可以保留有效旧结果，避免接口波动导致全站反复退出推荐。

**完成标准：**

- 同一份内容，人工放行后不再被 SEO 错判成“审核未知”。
- 正文或链接目标改变，旧人工决定不能继续替新内容放行；审核规则版本变化时沿用现有有效性约束。
- 人工拒绝、封禁或删除后，页面搜索标记与推荐清单同步变化。
- 内容审核继续复用现有后台及本地规则，不调用外部审核模型。第二项的 AI 标题任务按本次要求使用现有接口处理必要的公开原文，是独立用途。

## 第二项：全自动生成有明确主题的标题，自然包含搜索词

**现在的问题：**大量标题直接截正文前 100 个字符，有时截到半句话，还看不出主题。

**目标：**每篇文章自动取得清晰标题，让搜索用户能看出它讲什么；日常运行不需要人工写标题、选关键词或批准结果。

**自动流程：**

1. **先提取原文。**清理 HTML、导航和无关链接；保留原文标题、关键段落及必要上下文。来源明确的文章标题可以直接使用；普通小标题不能自动冒充全文标题。排除纯链接、账号、泛用开场和明显残缺片段后仍不确定的，交给 AI 处理，不依赖“长于多少字”认定标题合格。
2. **需要时调用 AI。**无标题、标题过于笼统或像正文开场时，使用现有接口，让 AI 根据原文提炼主题、读者可能使用的搜索表达，并生成标题与摘要。
3. **自动检查再采用。**检查格式、长度、语言、关键词重复、原文依据，以及新增的人名、产品名、数字或夸大承诺。结果可疑时最多重新生成一次；仍不合格则使用规则提取的保守标题，不进入人工标题队列。
4. **保存并复用。**同一份正文生成一次后保存；读者打开页面时直接显示结果。正文实质变化后才重新生成，避免每次访问调用 AI、拖慢页面或反复变标题。

**搜索词怎么进入标题：**

- AI 提炼一个核心主题词及必要的场景词，例如“Docker 容器”与“无法访问网络”，自然组成标题。
- 优先描述内容实际解决的问题；教程、经验、观点、新闻要准确区分，不能把一段讨论包装成完整教程。
- 例如原文确实介绍 Docker 容器网络排查时，可以生成“Docker 容器无法访问网络：排查步骤与解决方法”。原文只提出问题时，则不能使用“解决方法”。
- 不批量拼接“最新、最全、免费、2026”等正文无依据的词，也不重复堆叠关键词。搜索词主要用于标题和真实页面表达，不新增 `meta keywords`。
- 这里得到的是基于内容推测的搜索表达，不是经过搜索量工具验证的热门词。后续结合 Search Console 的真实查询验证，不把 AI 猜测标成“高流量关键词”。

**接口与模型：**核对过的线上 v1.9.7 源码已有 `lib/siliconflow.js` 与 SiliconFlow 文本接口。复用服务地址、密钥读取和请求封装；标题使用独立的模型配置，不直接沿用偏翻译用途的默认模型。开发时根据账号实际可用的通用指令模型验证中文、英文及结构化输出效果，再确定模型，本文不宣称某个模型当前已可用。

AI 仅处理内容审核通过且具备推荐候选资格的公开存档；发送生成所需的原文文本，不发送后台资料、投诉信息、凭证或访客信息。首版把输入预算作为硬上限：超限长文直接使用本地提取标题，不截取部分正文后假装理解全文，也不拆成多次付费调用。内容里的指令一律作为被处理文本，不能改变系统任务或调用工具。

原文以用户提供的公开存档为范围，不让模型联网抓取、打开正文里的链接或猜测图片／视频内容。未纳入输入的媒体不能被描述成模型已理解的事实；仅靠媒体才能判断主题时使用原文配文兜底。

**生成与兜底要求：**

- 优先正文主体语言；不把所有外文标题强制改成中文。标题长度按语言与可读性控制，在词句边界收束，不把固定字数称为 Google 标准。
- AI 返回结构化的标题、摘要、主题词和对应原文依据。依据可验证存在于输入，但自动检查不能证明所有语义都绝对正确；不确定时采用更保守的表达。
- 明确禁止改变否定、条件和归属关系，例如把“不支持某功能”写成“支持某功能”，把作者猜测写成已证实结论。无法建立依据对应关系、输入被截断导致上下文不足时自动兜底；不把模型自报的高置信度当作正确证明。
- 执行超时、有限重试、并发和每日 token 预算控制；初始并发 1，历史内容分批生成。费用硬上限默认每日 1 元、每月 20 元（人民币，UTC 日/月边界）；请求前按配置的模型输入/输出单价及最大 token 预留费用，余额不足立即使用原文兜底。价格未配置或无效时不发请求。历史首批最多 20 篇，不自动扩量。
- 请求设置最大输入、最大输出及总调用次数；质量重写最多一次，主备模型切换也计入同一任务总预算，不能层层重试放大费用。429 按退避及服务端等待时间处理，鉴权或余额错误暂停队列并兜底；网络类失败只做有限延迟重试。
- 标题任务的队列和用量统计独立于翻译，但共享服务商限额时优先保障用户正在发起的翻译。预算预留在发送前完成，进程重启不清零；记录请求消耗、实际模型与失败类型，日志不写密钥或整段正文。
- 接口故障、额度不足或结果不合格均自动使用原文标题或完整句提取。没有合适句子时按词语边界保守截取并使用省略号。记录技术原因，日常不要求管理员处理。超时或计费不明的请求保留全额预留，不把未知消耗当作免费。
- AI 等待或失败不阻断存档发布，不单独改变允许收录状态；AI 写出好标题也不能让低质量正文通过准入。
- 不因每日重评反复调用 AI。生成缓存绑定正文指纹、语言和提示词版本；正文变化后旧结果失效并使用当前原文兜底。模型或提示词升级先试算再迁移。
- 原文标题已经合格时，摘要走本地完整句提取，不因缺少 AI 摘要而额外调用。主题词只作生成与效果分析数据，不自动创建标签页、站内搜索落地页或额外收录入口。

标题、页面 H1、分享卡片、列表及结构化数据采用同一份最终标题。原文已有标题文本仍保留；增加生成的 H1 时将原文标题规范为适当下级标题，避免双 H1。摘要在同一次调用中生成并检查，不单独增加必需人工步骤。后台只需显示结果、来源和生成状态，不建设逐篇标题审批流程。

**完成标准：**无需人工操作即可完成“提取／AI 生成／验证／保存／失败兜底”；标题能说明主题且不堆词；测试集中无依据的年份、数据、承诺及否定关系错误被拦截或降级；中英文、长文、无标题和恶意指令样本均有验证。这些检查降低错误概率，不承诺任意内容都能被自动正确概括。原文、图片、视频和翻译展示通过回归检查。上线前的抽样质量测试属于开发验收，不转化为每篇文章的人工生产步骤。

## 第三项：文字够长，也要检查有没有重复灌水

**现在的问题：**重复同一个词也可以凑够长度，进入推荐清单。

**怎么改：**在现有基本条件之外，先检查正文是否存在明显异常，再计算有效信息量。

| 内容情况 | 新处理方式 |
| --- | --- |
| 同一词或同一句反复重复 | 重复部分不反复累计有效长度；明显异常暂不自动推荐 |
| 大量模板话术，实际正文很少 | 标记具体原因，进入待检查 |
| 正文残缺、关键媒体未完成 | 暂不推荐，修复后重新判断 |
| 完整、可读的纯文字长文 | 仍有自动推荐机会，不要求必须配图 |
| 很短但实际很有价值的内容 | 允许管理员在现有后台人工推荐 |
| 代码、诗歌、编号列表等特殊格式 | 不因单一重复指标直接判为垃圾，边界情况进入待检查 |

重复率、句段长度等阈值放进配置。先用现有内容与测试样本验证，再确定首版值，不随意宣布一个“Google 质量分”。本轮覆盖明显机械重复和简单模板信号，不承诺自动识别所有近似转载、事实错误或搜索需求。

当前“长文可独立通过”改为“去除重复影响后仍有足够正文、基本条件完整且未命中质量异常，才可自动推荐”。疑似异常使用“待检查”，空内容和明确不合格内容继续暂不推荐。人工推荐可以处理质量边界，但不能绕过审核、删除、封禁及既有重复限制。

**处理顺序固定：原文及有效审核结论 → 质量筛选 → 自动标题 → 页面输出。**质量评估只使用原始正文和真实媒体状态。AI 标题、摘要、关键词、生成的 H1 均不计入正文长度、原文标题加分或内容去重依据，避免形成“AI 包装后自动升格”的循环。仅因新增或修改生成标题，不能触发收录资格变化。

“等待检查”针对内容质量与审核边界，不是标题审批。正常内容仍自动流转；技术等待类状态如媒体下载完成后自动重评，语义争议才保留现有人工例外通道。

**完成标准：**重复一个词 160 次不再自动通过；真实无图长文仍有通过路径；疑似异常在后台看得到具体原因，管理员能纠正误判。

## 第四项：在同一个后台把状态说清楚

后台分别显示两个维度，避免把审核与搜索混为一谈：

| 维度 | 给管理员看的说法 |
| --- | --- |
| 内容审核 | 允许发布／等待审核／拒绝发布 |
| 搜索推荐 | 允许搜索引擎收录／等待检查／暂不推荐收录 |

展示具体原因，例如“重复句段较多”“来源时间缺失”“媒体尚未完成”，并保留已有的推荐、撤回和重新评估操作。人工操作记录时间、原因与适用内容版本。

“允许搜索引擎收录”表示网站发出的意愿，不展示成“Google 已收录”。Google 实际情况由 Search Console 核对；本版不建设复杂的自动数据同步后台。

## 第五项：分批应用，先看变化再扩大

1. **开发和离线验证。**修复审核衔接、标题和筛选，覆盖正常内容、异常内容、人工决定与内容变化。
2. **对现有数据只试算。**生成旧状态、新状态、变化原因及标题前后对照，不改变线上状态。优先检查所有降级候选、原先依靠长度通过的页面，以及不同语言和格式的样本。
3. **小批量应用。**质量规则先应用于抽查过的页面及新存档，再逐批处理历史页；审核拒绝、删除与封禁仍立即生效。管理员可看进度、失败原因并重试。
4. **上线检查。**复查推荐清单与页面标记一致、公开页面正常、标题清晰、原文和媒体完整、移动端布局正常。

新版质量规则必须有独立启用控制：不能因为应用代码升级、规则版本号变化或每日重评，就自动把全部历史页面套用新规则。试算、分批迁移及定时任务采用同一套版本选择策略。

质量规则启用和 AI 标题启用分开控制，可以分别回退。开发、测试和回滚均使用兼容追加字段；原始正文不被生成标题覆盖，既有短码、canonical 和来源链接保持稳定，标题变化不创建新 URL。

标题和摘要上线时，服务端 HTML、列表、分享卡片和结构化数据一起读取已保存结果；任何旧页面／列表缓存需同时失效，不能等用户触发重新保存才更新。浏览器与搜索爬虫获得同一份内容。继续不输出无法证明的 sitemap `lastmod`，不把每次调度时间当作正文更新时间。

保存旧推荐状态、规则版本及标题配置快照。需要回退时只恢复本次变更且其后未被修改的记录；发布之后的新投诉、删除、封禁和人工决定必须保留。不能用整库回滚覆盖新业务数据。

## 第六项：确认 Google 到底有没有带来访问

网站开发完成后，接入或检查 Search Console，并在现有统计后台核对访问与事件接收。账号、域名验证或后台访问缺失时，明确列出所需条件，不把这部分标成完成。

先选约 20–30 篇主题明确、信息完整的存档作观察组，优先覆盖已存在的有用内容。这个数量用于控制人工检查成本，不是 Google 要求。记录入组时间和规则版本，不为实验重新堆写正文。

| 要回答的问题 | 查看什么 |
| --- | --- |
| Google 是否收录？ | Search Console 的网页索引及样本网址检查 |
| 别人在搜什么？ | 带来展示的搜索词与对应页面 |
| 标题是否吸引合适的人？ | 展示、点击与点击率，结合查询和位置一起看 |
| 来访是否有业务价值？ | 从自然搜索进入后是否浏览更多内容、使用翻译、开始或完成存档 |

沿用现有事件，先核对正常浏览器触发与后台接收，避免重复统计；不向统计系统上传正文、用户提交链接或投诉联系方式。

观察 4–8 周后再决定扩大哪些主题、调整哪些规则。数据不足就继续观察，不把前后波动直接解释为本次改动带来的因果效果，也不承诺多久收录或带来多少流量。

Google 可以重写搜索结果标题和摘要，页面修改后也需等待重新抓取。验收以站点输出和真实搜索趋势为准，不要求搜索结果立即逐字使用生成标题，也不因短期未展示就反复改写标题。

## 开发落点与关键测试

这部分用于开发交接，产品判断以上面的行为为准。

- `lib/moderation-review.js`、`lib/seo-store.js`、审核路由：共享有效审核结果；使用同一份内容快照评估，写入前校验未改变。审核状态变化及时使旧推荐结果失效，后台重评失败时显示原因并重试，不能继续展示失效的允许状态。
- `lib/seo.js`、`config/seo-rules.json`：增加重复信息处理与异常原因，区分旧规则、新规则和试算结果；规则函数保持可测试。
- AI 元数据任务、页面渲染与现有后台：复用 SiliconFlow 接口，单独配置通用标题模型；保存标题、摘要、主题词、原文依据、内容指纹、提示词版本、生成来源和状态。统一公开页面及列表的标题来源；AI 输出视为不可信输入，做解析、校验和输出转义。
- AI 任务使用持久化队列、唯一任务键、并发及预算限制；结果提交前重新检查内容指纹、审核及删除状态，失效结果丢弃。原文或媒体下载完成不能被旧任务覆盖；API 故障时自动兜底且不无限重试。
- 审核、质量与标题使用可追溯的同一内容版本，但不强行共用一个不合适的哈希。保留来源身份、正文和链接目标的有效审核关联，单纯本地媒体路径替换／渲染标签变化不能误作正文变更；正文或目标链接真正变化不能被忽略。生成字段另存，不进入原文指纹。开发须验证“保存前审核 → 图片本地化 → 保存后 SEO”全过程，不能只拿完全相同的测试字符串证明衔接成功。
- 重评脚本与调度：提供只读差异清单、分批应用与版本控制；追加字段兼容旧数据；按记录校验内容与人工操作没有并发变化。
- 测试至少包含：人工允许/拒绝、审核版本失效、正文与链接变更、重评失败、并发更新、重复词句、合法长文、代码列表、中英文标题、HTML 注入边界、唯一 H1、媒体翻译保留、sitemap 与 robots 一致；另覆盖 AI 超时、429/鉴权失败、异常 JSON、编造数字、关键词堆叠、提示词注入、重复任务、预算耗尽及旧结果覆盖新正文。

发布前开发验收还必须覆盖：AI 标题不能给质量评分加分、普通 H2 不被错认作全文标题、否定和引用不被改写成事实、长文和媒体上下文不足自动兜底、重启不重复消耗任务预算、AI 关闭后服务正常，以及现有标题/媒体/翻译缓存不会产生串版。

本版确定模型为 Qwen2.5-7B-Instruct，输入上界 8192、输出最多 512 tokens、每篇内容版本最多 2 次调用、并发 1、每天最多 40 次、每月最多 1200 次。预算最高 1 元/天、20 元/月；报价设有效期，到期停止调用。重复异常首版阈值为正文至少 40 个有效单位且重复占比达到 60%，只作初筛不代表搜索价值评分；实现及验证边界记录于交付说明。上线所需外部账号访问与网站代码验收分别记录。

## 怎么判断这一版完成

网站部分完成：审核衔接正确，明显灌水无法自动推荐，标题全自动生成且失败可自动兜底，后台状态明确，历史数据分批处理可追溯，公开检查通过。

效果验证完成：Search Console 与统计接收已核验，观察组有可回看的数据。网站可以先发布；没有外部数据时必须将效果验证标为未完成，不把“代码上线”等同于“搜索流量增长已实现”。
